# CP02 domain lifecycle — local implementation status

**Updated:** 17 September 2026 · **Status:** in progress, not a custom-domain release

The default `{workspace.slug}.wodana.ai` login address remains the only route we consider usable. Workspace slugs and tenant login slugs are unique in PostgreSQL. A custom hostname is not live when an operator types it, requests it, or verifies its TXT record. The operator portal keeps the Wodana address visible as the fallback.

## Implemented locally

- `workspace_domains` is tenant-scoped and records one globally unique live reservation per hostname. The active-routing database constraint requires verified DNS, an issued certificate and an activation timestamp. Removal is refused while certificate issuance or routing is pending/active. The migration was applied to the loopback `wodana` test database only.
- Operator-only Business Core API: list, idempotent request, TXT verification, challenge rotation and pre-activation removal. Requests normalize/reject unsafe and Wodana-owned hostnames, produce a unique 48-hour TXT challenge, require version checks for later commands and attribute changes to the human operator audit. An old TXT token cannot verify a rotated or transferred request.
- DNS lookup failures and no-record responses are distinct. A successful ownership check moves the certificate state to `manual_setup_required`; routing stays `not_requested`. There is no button or API that can mark a hostname active from the operator portal.
- The internal web BFF checks operator session and same-origin writes, and the inspector uses the shared form, button, badge, callout, skeleton and confirmation components. It shows copyable TXT name/value and separate DNS/certificate/routing state. There is no tenant-workspace link or admin feature in the staff mobile app.
- Tenant status reports a requested domain truthfully, preferring an active one when more than one request exists. After removal it returns `not_configured` again.
- A public custom-host resolver only returns a tenant when its organization is active, routing is active, DNS ownership was checked in the last seven days, and the issued certificate has not expired. Its narrow `SECURITY DEFINER` function exposes only login branding, because the runtime database role cannot read the RLS-protected domain table before a tenant session exists. Unknown and expired hosts fail closed. Web `/login`, the root redirect, sign-in and password recovery do not fall back to Iglo on an unbound custom Host or accept a different tenant slug supplied by the browser. This is a routing guard, not proof of real ingress/TLS automation.
- Operators can recheck an already verified TXT challenge. A missing record marks ownership failed, denies host resolution immediately and puts any active/pending route or issued/pending certificate into `rollback pending`. The certificate remains recorded as issued until physical cleanup is confirmed; the hostname cannot be released or assigned to another tenant while rollback is pending. A DNS resolver outage leaves the previous state/version unchanged and returns a retryable error. Recovery requires a new code after rollback. Automatic recheck scheduling and the physical rollback worker are still open.

## Local evidence

- `DOMAIN_TEST_DATABASE_URL=postgresql://<local-user>@127.0.0.1:5432/wodana node --import tsx scripts/smoke-domain-lifecycle.mjs` from `services/business-core`: passed reservation/replay, cross-tenant denial, TXT rotation/proof, manual TLS hold, removal, fresh proof on transfer, current/expired certificate, resolver outage without a state change, and missing ownership with fail-closed host resolution and pending rollback. Synthetic rows were removed.
- `PLATFORM_TEST_DOMAIN_API=true node scripts/smoke-platform-operator.mjs` against rebuilt local APIs on loopback ports 8025 and 8026: passed guarded HTTP endpoints, status transitions, the versioned recheck route's pre-verification refusal and human audit, along with operator MFA/session checks. The earlier combined run against a separately built local web preview on port 3102 passed the BFF/browser path and desktop/mobile no-horizontal-overflow checks; the later recheck UI was validated by focused component tests, not a fresh visual capture. Synthetic users/workspaces/domains were cleaned.
- Focused backend `typecheck` and domain/tenant-management tests passed; web `typecheck`, focused portal/BFF tests (2 files, 10 tests) and production build passed. Visual fixtures are in [the CP02 evidence folder](evidence/cp02/README.md). The visual route used a synthetic DNS response, not a real certificate or public hostname.
- A host-guard smoke against the rebuilt loopback API/web returned **404** for an unbound custom `/login`, **200** for a known Wodana tenant login, **404** for an unbound Host on the login BFF, and **400** for a forged tenant slug on a known tenant Host. The direct database smoke inserted a **synthetic-only** active/certificate row, switched to the non-`BYPASSRLS` `wodana_app` role, proved direct domain rows stay hidden while exact-host sign-in lookup works, and proved denial after synthetic expiry and as soon as rollback becomes pending. It also exercised reservation/list under the same runtime role, then removed the rows. No TLS provider or real custom hostname was contacted.

## Still required before CP02.1 can be checked off

1. Infrastructure adapter/worker for certificate request, issuance, renewal and failure receipts. No certificate-provider receipt exists locally or for Palm; the state must remain `manual_setup_required`.
2. Safe ingress/vhost routing command and probe with a hostname-to-tenant binding; validate the reverse proxy and all invitation/auth callback origins. The app now rejects unknown Host and cross-tenant login slugs, but a DNS-verified row cannot be used for sign-in until HTTPS, routing and tenant binding are independently observed.
3. Schedule DNS/certificate rechecks and run reversible physical rollback before releasing an active hostname. The operator-triggered ownership recheck and immediate application-side denial now work locally; provider outage, renewal failure, ingress cleanup and transfer after physical rollback still need adapter/worker acceptance.
4. Then CP02.2 finishes the operator UI for retry/rollback and centrally approved brand previews; CP02.3 connects active custom hosts to login, invitation/public forms/client links and native app links. No Palm DNS or deployment change follows automatically.

The portal intentionally does not show an “active” custom-domain badge from a manually entered hostname or a TXT proof alone.
