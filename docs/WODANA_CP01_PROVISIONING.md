# CP01 provisioning contract

**Status:** CP01.1 local API slice verified on 17 September 2026; operator UI, owner-app UAT, real provider delivery and deployed acceptance remain separate tasks.

## Identity and defaults

One customer account is the contract/contact relationship and may own multiple isolated organizations. Its display name and contract contact are entered once, separately from the first organization's display name, login slug, legal entity and owner. The owner is an invited user, not automatically the billing/contract contact. A new account-level `trial_uncontracted` commercial record pins its trial plan without pretending that a signed contract or price exists; the organization subscription remains a compatibility allocation. Existing `/internal/tenants` routes remain compatibility paths; new operator flows use a draft followed by an explicit provision command.

An operator selects immutable `(code, version)` profiles for **region**, **firm kit** and **plan**. The draft stores those exact versions. Provisioning resolves the pinned profiles, creates the first organization, and records the selected versions/snapshot with it. Profile edits publish a new version; existing tenants never silently inherit a changed default. The plan profile initializes trial terms, not a sold commercial entitlement (CP04). The selectable **Design & build v2** kit pins the existing four-stage project workflow and installs it as the organization's default project-workflow template in the same provisioning transaction. Label-only v1 firm kits are retained for history but hidden from new drafts; additional operational kits belong to P10.1. This is a project workflow starter, not a claim that all pre-execution, CRM or catalog configuration is complete.

## State and commands

`POST /internal/operator/tenant-drafts` validates account/organization/owner separately, pins the three profile versions, reserves an unused slug with an expiry, and returns a draft ID and version. An `Idempotency-Key` is required: same key + same normalized request replays the draft; a different request returns 409. A conflict with an existing workspace, login slug, or live reservation returns 409. Secrets and invitation tokens are absent from draft reads.

`GET /internal/operator/tenant-drafts/:id` shows `draft`, `provisioning`, `provisioned` or `failed`, the exact selected versions and reservation expiry. `POST /internal/operator/tenant-drafts/:id/provision` requires the draft's expected version and an idempotency key. It moves draft → provisioning, calls the existing idempotent workspace foundation once, and records the resulting workspace. A retry reconciles a previous commit through the external tenant ID; it cannot create a second account/organization. A failed step retains an actionable error code and permits retry after correction or a new draft. A stale expected version returns 409.

Owner invitation creation and delivery are distinct. The token is returned once on creation/rotation and never stored in plaintext. The operator `send` command requires an idempotency key; replay returns status without a token or second email. A deliberate `resend` rotates again. Delivery writes `pending/sent/not_configured/failed` status, attempt time and provider receipt (if any), and audits the human operator/correlation ID. Superseded send commands remain distinguishable. A failed or unconfigured provider must not be shown as sent. An expired/lost token can be rotated; an accepted/cancelled invitation cannot be resent. The legacy token-returning route remains available during migration, but must not claim email delivery.

Onboarding checkpoints are per organization and versioned. Each completed step stays durable across a retry/reload, with the next required step derived from the stored state. Invitation delivery failure does not erase the organization or reset onboarding. Neither draft creation nor initial provisioning changes Palm live data without a separately authorized release.

## Acceptance matrix

- Same-account multi-organization identity and distinct account/organization names; owner different from contract contact.
- Profile version pinning; slug collision and reservation expiry/reuse; idempotency replay and conflicting body/key.
- Draft → provisioned retry after a simulated partial response loss, stale version rejection, no duplicate organization.
- Invitation not requested, sent, not configured, failed, expired and rotated states; no token on reads or replay.
- Existing routes still work; tenant/user cross-account reads are denied; operator audit attributes every command.
- Onboarding resumes after interruption, and local synthetic records are cleaned with no Palm or deployed mutation.

Local API smoke runs as `wodana_app` against a loopback PostgreSQL server. Its negative cases include a slug hidden by tenant RLS, expiry/reuse of a reservation, wrong profile version, stale draft version, lost response after core commit, unconfigured Mailgun and a failing loopback Mailgun endpoint. The script verifies account-contract RLS, existing-owner name preservation, audit attribution and exact synthetic cleanup. These are local acceptance checks, not a provider receipt or production release.

The final CP01.1 pass applied migrations `0079`–`0083` only to loopback `wodana`; Business Core build and web typecheck passed, five focused Business Core spec files passed (12 tests), and the synthetic HTTP smoke passed against both an unconfigured email provider and a deliberately failing loopback provider. The smoke asserts the pinned v2 kit, hidden label-only v1 kits, and actual default project-workflow row/stages. It cleaned its synthetic organizations/accounts/drafts. No Palm live data, real email provider or deployed service was changed.

CP01.2 uses a dedicated operator-only `/internal/new` page rather than a create modal. Account, organization, contract contact and owner are separate in the review; organization name/login slug are prefilled from the account name but remain independently editable. The region/firm-kit/plan choices come from selectable versioned profiles. The BFF forwards explicit idempotency keys to draft, provision and invitation-send commands. A created customer shows real readiness and delivery states, never a false “sent”; a manual activation link is transient and shown only to the operator when email has not been confirmed. A local browser smoke covered operator MFA, page/review in light/dark desktop/mobile, a synthetic BFF creation and `not_configured` invitation outcome. Captures are in [CP01 visual evidence](evidence/cp01/README.md).

## CP01.3 local owner acceptance

The operator browser smoke now continues from its one-time manual link into a fresh mobile-width browser context. The synthetic owner activates the invitation, enrolls an authenticator, saves recovery codes, completes all four onboarding steps and opens CRM. The same smoke then uses the native `AuthClient` against the live loopback Business Core: password login returns an MFA challenge with no persisted token; a recovery-code verification establishes the selected-tenant session and permitted CRM module; sign-out clears storage. The generic native build accepts a workspace code instead of silently defaulting to Iglo, and an unfinished onboarding state cannot open native Home. The Expo web-preview proxy now forwards MFA challenges and keeps the refresh token HttpOnly after verification.

The API smoke additionally rejects an expired link and rotated link, rejects onboarding completion before required steps, confirms idempotent draft/send replays, and exercises both `not_configured` and deliberately failed email delivery. Both smokes delete only their exact synthetic users, workspaces, accounts and drafts; a follow-up local database count was zero. On 17 September 2026, the operator/browser/native-client smoke passed with `PLATFORM_TEST_NATIVE_AUTH=true` using `node --import tsx`; the draft smoke passed against loopback Business Core ports 8023 and 8024. Mobile typecheck and 46 tests passed; `expo export --platform all` produced iOS, Android and web bundles. The mobile-width owner onboarding and CRM screenshots were inspected for horizontal overflow and are indexed in [CP01 visual evidence](evidence/cp01/README.md).

This is local acceptance, not a real email receipt, physical-device run, verified domain/universal-link handoff or Palm production sign-off. The owner invitation is a tenant-scoped web URL usable in a mobile browser; native app-link association and custom-domain routing are CP02.3. Email remains honestly `not_configured` unless a provider is configured and its receipt is verified.
