# Slice 1B — delivery quantity planning

Journey: Item → Supply & site plan → Delivery quantities → add deliveries and their source consumption → save draft → confirm quantities. Keep the ordinary single-item flow available. Existing shared DataGrid, fields, buttons and modal are the UI vocabulary.

A package remains the sole commercial owner of its released scope. A quantity plan describes delivery rows within that package, not duplicate BOQ rows or new purchase commitments. Each row has stable ID, title, positive delivery quantity, explicit unit, source allocations (scope-line ID and positive quantity in that source's unit), and a measurement basis. Multiple source units are never summed. A conversion or bundled/multiple-line source requires an explanation; this is a recorded planning basis, not an automatic engineering conversion. Per source, allocated quantity cannot exceed released quantity; confirmation requires exact coverage. Task output, delivery quantities and commercial quantities remain distinct.

API: existing project command endpoint, new delivery_quantities and revise_delivery_quantities actions, stable requestId and project revision use existing transactional conflict/retry controls. Nested quantity-plan version adds record-level protection. Both require projects.manage. Draft save allows incomplete coverage, but all entered rows must be valid. Confirm records actor/time and server-captured source revision evidence. Confirmed rows cannot be overwritten. Revise requires a reason, archives the confirmed version, and returns a new draft; existing work/output/orders/receipts/stock movements block amendments pending impact review. Cancelled/completed items cannot be edited. No command changes package readiness, releases purchases or sends external messages.

Readiness: if an explicit quantity plan exists, it must be confirmed and still match active source quantities/versions before work release/start. Legacy items without a quantity plan remain compatible; do not manufacture historical allocation facts. Factory runs, stock, partial QC and dispatch do not yet consume these rows; downstream allocation binding is a later slice.

RFA contract remains a separate next slice: version-bound source snapshot; named submitter and reviewer; required decision scope; submit/review/approve/return/reject/withdraw/revise commands; independent authority and stale-source checks; immutable decisions/history; internal visibility first, explicit publishing before portal visibility. RFA approval is not quantity confirmation, commercial release, resource booking or purchase approval. No RFA tab should be exposed before its command and queue are connected.

## Implemented and verified

The local item editor now opens Delivery quantities. The shared CRM grid lists delivery rows; shared fields edit a row and its per-source allocations. Drafts, confirmation, reasoned revision and prior confirmation history are connected to the existing project command endpoint. A confirmed quantity plan retains server-captured source evidence. Readiness and task-start commands reject an explicit unconfirmed or stale plan. The source-line selector now consistently excludes deducted scope. Classification and quantity changes share the same commitment guard.

Verification: 98 backend tests across seven relevant suites; 34 UI tests across quantity editor, item planner and workspace; web/backend typechecks; scoped UI lint. Six browser checks passed across desktop/mobile, including the populated six-plus-four editor, keyboard input, LTR/RTL overflow and failed-save draft retention. Screenshots inspected on both viewport sizes. The populated browser scenario intercepts all project API requests and deliberately simulates a conflict; persistence and command rules are tested separately in the backend, not represented as a live database end-to-end test. No customer project activated, no deployment, no external communication.

Remaining: bind confirmed delivery-row IDs to task output, material/stock allocations, QC and dispatch in their owning slices. Until then these rows are quantity planning only, not shipment/installation records. RFA is documented above but not implemented by this quantity-planning slice.
