# P00.3 — transition gates and permissions (accepted local baseline)

**18 September 2026. Local code audit and engineering decision record.** This reconciles current commands with the [four-gate product contract](WODANA_PRODUCT_BLUEPRINT.md#4-lifecycle-and-gate-rules). It is not deployed/Palm UAT. `H` means one of the four non-overrideable **business** gates; `I` means a non-overrideable integrity/security/accounting/evidence rule; `W` is a possible future operational warning. No generic `W` override is authorized or shipped: every current guard remains hard unless a later named rule receives an explicit permission, reason and audit contract.

## Decision findings that affect release

1. **H3 uses explicit accepted business data.** `requiredForProduction` is stored on the payment term, copied to the agreement payment and frozen project baseline, and displayed in the quotation/payment UI. Factory `task_status=in_progress` rechecks every applicable milestone using finance-verified receipt/allocation truth. Free-text titles/triggers are never parsed to infer a gate. [Execution service](../services/business-core/src/projects/execution.service.ts), [payment type](../services/business-core/src/commercial/commercial.types.ts).
2. **H2 cannot pass on an empty set.** A submitted base quotation must identify at least one `requiredForRelease` milestone. Release rechecks that a required milestone exists and that every required amount is backed by a full, operational, finance-verified receipt allocation bound to the contract identity. [Release integrity](../services/business-core/src/commercial/release-integrity.ts), [payment terms](../services/business-core/src/commercial/commercial.domain.ts).
3. **H1 and H2 are independent prerequisites of release.** Owner Review approval requires the accepted revision, operational matching agreement, truthful checklist, exact material approvals and independent authorized reviewer; it no longer waits for the receipt. Execution release still requires both the approved Deal File and H2. [Owner decision](../services/business-core/src/commercial/commercial.service.ts), [release integrity](../services/business-core/src/commercial/release-integrity.ts).
4. **Finance verification is now a distinct local permission and record transition.** `commercial.finance.verify` is separate from quote approval, Owner Review, agreement execution and release; default system owner/administrator roles receive it for migration continuity and custom team roles can be assigned it through the existing role editor. Manual receipt reporting and finance verification are separate commands and the reporter cannot verify their own manual receipt. A provider settlement is recorded as `provider_confirmed`, not finance verified. Exact Palm role assignment and regional compliance are still acceptance/configuration work. [Permission migration](../services/business-core/drizzle/0095_commercial_finance_permission.sql), [command dispatch](../services/business-core/src/commercial/commercial.service.ts), [structured ledger](../services/business-core/src/commercial/finance-ledger.ts).
5. **H4 accepts two attributable evidence paths.** The preferred client portal decision is purpose-bound to the assigned client and challenge. The controlled signed-record fallback requires the current immutable handover pack, `projects.review`, a named client signatory and signed-evidence reference; completion still requires every pack accepted. Regional/legal policy may later require a stored signature artifact or second verifier, but neither can be represented as already validated. [Handover command](../services/business-core/src/projects/execution.domain.ts), [client decision](../services/business-core/src/projects/project-handover.ts).
6. **Many non-business readiness checks are presently hard blocks.** Quote submission needs a verified measurement, site plan, linked approved designs, current client-confirmed definition, and other preparation checks; release needs approved designs/materials and all change requests closed; project readiness, stage progression, handover and completion block on operational checks. These are not automatically safe to override—scope/version/evidence truth remains invariant—but they must be split into invariant facts versus policy recommendations before a compliant exception UX exists.

### Default workflow exit-key mapping

The frozen template defaults to `planning` (`project_manager_assigned`, `tasks_planned`) → `delivery` (`all_tasks_closed`, `all_snags_closed`) → `handover` (`all_handovers_accepted`, `finance_closed`) → `completed`. `workflow_transition` currently enforces every configured exit key; `complete_project` separately enforces closeout. `all_handovers_accepted` is H4 at completion; `finance_closed` includes accounting truth (`I`), but making it a prerequisite for client handover/phase change is a `W` candidate. The owner/tasks/snags exit keys are `W` candidates, not extra business hard gates. A workspace template must never be able to delete H1–H4 or a source invariant. [Workflow source](../services/business-core/src/projects/project-workflow.ts#L94).

## Required server contract and audit before an override exists

- Return structured rejection (`ruleCode`, `classification`, `recordId`, `sourceVersion`, `reason`, `nextAction`, `canRequestOverride`) from the same server rule used by the command. `403` for authorization, `409` for stale/revision/transition conflict and `422` for invalid evidence/input; never show an override CTA for H/I. Current plain-text conflicts remain until a versioned contract is introduced.
- An authorized `W` override is a *new explicit command*, never a suppressed frontend error or a boolean embedded in the ordinary request. Require exact rule/version, workspace/legal entity, Job/case/project and source IDs, decision snapshot hash, named actor/effective permission/team, reason, affected scope, risk owner, optional expiry and idempotency key. Audit before/after, request/correlation ID, server timestamp and approver; expose it in the Job timeline and compliance report. A changed underlying revision invalidates an unconsumed approval.
- UI shows the reason in one concise sentence, the exact affected item, primary “Fix now,” and “Request exception” **only** for signed-off `W` rules. The request asks for a reason and displays who can authorize it; subsequent action still displays “Proceed with approved exception.” Do not color a blocked step as complete. On mobile, the same warning and approval state must be server-owned, not a local bypass.
- Client-facing packets and reports reveal only approved exceptions relevant to the client's decision; never disclose internal margins, staff notes or raw audit metadata. An exception cannot change accounting balances, accepted revisions, physical quantities or evidence source.
